## Подробные находки и рекомендации

### 1. P1 — изображения Recipe: обязательное поле отсутствует у проверенных рецептов

**Подтверждено в коде и HTML двух рецептов.** [template-parts/schema.php](../template-parts/schema.php), строки 37–55, добавляет `image` только при наличии миниатюры или картинки шага. Оба проверенных рецепта не содержат этого свойства. Визуальная заглушка `no_image.png` не является фотографией блюда и не должна подставляться в Recipe ради прохождения проверки.

Кроме того, строка 50 помещает все картинки шагов в общий `Recipe.image`. При заполненных шагах туда могут попасть ингредиенты или процесс приготовления. Изображения шагов в [template-parts/content-recipe.php](../template-parts/content-recipe.php), строки 183–194, вообще не выводятся.

**Исправить:** обеспечить настоящую фотографию готового блюда; в `Recipe.image` использовать только подходящие фотографии блюда, а в `HowToStep.image` — фотографию конкретного шага, видимую рядом с ним. Добавить редакционную проверку полноты, не меняя молча статусы старых записей. Предусмотреть доступные варианты 1:1, 4:3 и 16:9, если исходники позволяют качественное кадрирование.

**Критерий:** у проверяемых рецептов есть доступный URL реального изображения; разметка соответствует HTML и проходит проверку обязательных свойств. В Google Recipe `name` и `image` обязательны; рекомендации к изображениям приведены в [документации Recipe](https://developers.google.com/search/docs/appearance/structured-data/recipe).

### 2. P1 — пищевая ценность «на 100 г» используется для Recipe без пересчёта на порцию

**Подтверждено.** [template-parts/schema.php](../template-parts/schema.php), строки 96–104, жёстко задаёт `servingSize: "100 g"`. [template-parts/content-recipe.php](../template-parts/content-recipe.php), строки 132–162, показывает те же значения как питание на 100 г. Число порций добавляется отдельно. Например, у проверенной пшённой каши указаны 4 порции и `calories: "951 kcal"` при `servingSize: "100 g"`.

**Исправить:** сначала проверить смысл импортированных чисел, затем хранить/рассчитывать достоверные значения на порцию. Для пересчёта с 100 г нужна масса порции или готового блюда: деление только на число порций некорректно. До уточнения данных не отправлять сомнительные значения в Google Recipe; необязательное nutrition можно опустить. Не исправлять исторические числа автоматически.

**Критерий:** видимая единица измерения согласована с JSON-LD; при передаче калорий заполнено достоверное число порций. Google описывает `nutrition.calories` как калории на порцию: [Recipe — nutrition](https://developers.google.com/search/docs/appearance/structured-data/recipe#nutrition-calories).

### 3. P1 — BreadcrumbList на странице 2 содержит промежуточный элемент без URL

**Подтверждено в HTML `/recipes/page/2/`.** [functions-parts/breadcrumbs.php](../functions-parts/breadcrumbs.php), строки 70–86, добавляет текущий раздел без URL, а затем ещё один элемент «Страница 2» без URL. В итоге крошка «Каталог рецептов» перестаёт быть последней, но остаётся без `item`.

**Исправить:** при добавлении номера страницы сделать предыдущий элемент ссылкой на исходный архив/запись либо вынести номер страницы за пределы размеченной цепочки. Аналогично проверить `cpage` комментариев. Согласовать цепочку с BreadcrumbList, который уже формирует Yoast; несколько цепочек допустимы, но каждая должна быть корректной.

**Критерий:** у каждого промежуточного элемента есть корректный URL и последовательная позиция. Исключение для отсутствующего `item` относится только к последнему элементу: [Google Breadcrumb](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb).

### 4. P1 — сброс ингредиентов может оставлять старые фильтры в URL

**Подтверждена логика и воспроизведён сценарий PHP/JS без базы.** [functions-parts/scripts_load.php](../functions-parts/scripts_load.php), строка 33, строит `base_url` через WordPress `remove_query_arg`. Массив `include_ingredients[]=milk` при этом сериализуется как `include_ingredients[0]=milk`. [static/js/filters.js](../static/js/filters.js), строки 23–30, удаляет только ключи без индекса и с пустыми скобками `[]`.

При очистке выбора `[0]=milk` остаётся в URL. При замене на `egg` получается одновременно `[0]=milk` и `[]=egg`. AJAX использует текущее состояние формы, а перезагрузка — объединённые параметры URL. Пользователь и робот могут получать разную подборку по одному ожидаемому состоянию навигации. Проблема относится также к исключаемым ингредиентам.

**Исправить:** перед сериализацией удалять все формы соответствующего ключа, включая числовые индексы; строить URL из нормализованного состояния. Убирать повторы, задавать устойчивый порядок ингредиентов, не сохранять пустые и стандартные значения вроде `sort_by=date`.

**Критерий:** выбор, замена и очистка ингредиентов после открытия сохранённой ссылки дают одинаковые URL и результаты при AJAX, полной перезагрузке и возврате браузером. Проверить и кириллические slug. Это функциональное исправление нуждается в регрессионном тесте.

### 5. P1 — необходима явная политика фасетов и индексации

**Подтверждено в коде; текущую публичную индексацию нельзя оценить из-за общего локального noindex.** [inc/recipe-query.php](../inc/recipe-query.php), строки 20–28 и 38–70, принимает категорию, подкатегорию, регион, включаемые и исключаемые ингредиенты, сортировку и страницу. Комбинации создают много URL. Синтаксическая очистка есть, но единой политики канонизации, индексации и проверки бессмысленных сочетаний в теме нет.

Локально `?region=seo-audit-nonexistent` возвращает пустую страницу с HTTP 200. Это риск soft 404 и обхода бесполезных комбинаций, а не подтверждение, что поисковик уже классифицировал её как soft 404. Несуществующая страница основного архива уже корректно возвращает 404.

**Рекомендуемая матрица после включения индексации production:**

| Тип URL | Политика |
| --- | --- |
| Рецепт, основной каталог, полезная категория | Доступны индексации; один canonical на собственный нормализованный URL; включены в sitemap |
| Страница 2+ полезного архива | Доступна обходу по HTML-ссылкам; canonical на эту страницу, а не на первую |
| Сортировка, произвольное сочетание ингредиентов/региона | По умолчанию исключить из индекса через согласованный `noindex`; не включать в sitemap |
| Подборка с отдельным поисковым спросом | Отдельная постоянная посадочная страница с полезным содержанием, ссылками и собственным canonical |
| Невалидные/противоречивые фасеты, несуществующая страница выдачи | 404 с понятным интерфейсом; не перенаправлять всё на каталог |
| Поиск, кабинет, личное избранное, редактор пользователя | `noindex`; убрать из sitemap; персональные данные защищать авторизацией |
| UTM и иные параметры, не меняющие содержимое | Canonical на чистый URL; при необходимости правила для действительно незначащих параметров |

Не объединять canonical все отличающиеся подборки с первой страницей каталога автоматически. Не применять Яндекс `Clean-param` к ингредиентам, регионам и пагинации: они меняют содержимое.

Сначала определить, какие URL должны индексироваться. `noindex` должен быть доступен роботу для чтения; запрет того же URL в `robots.txt` мешает увидеть директиву. Для ограничения избыточного обхода можно отдельно разработать правила robots.txt с учётом уже попавших в индекс URL. Canonical сам по себе не гарантирует экономию обхода. См. [Google о фасетной навигации](https://developers.google.com/crawling/docs/faceted-navigation), [robots meta](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag), [Яндекс robots.txt](https://yandex.ru/support/webmaster/ru/controlling-robot/robots-txt).

### 6. P1 — служебные и демонстрационные страницы присутствуют в sitemap

**Подтверждено на локальной копии.** `page-sitemap.xml` содержит кабинет и избранное, а также `/sample-page/`, `/user-feed/`, `/users/`, `/rcl-postedit/`. Для последних адресов назначение и содержимое нужно дополнительно проверить: список пользователей или лента могут быть осмысленной публичной частью проекта.

**Исправить:** для кабинета, личного избранного и редактора установить отдельное правило `noindex`, независимое от общего запрета тестовой среды, и исключение из sitemap. Демонстрационную страницу удалить/закрыть после проверки её назначения. Для авторов, стандартных post/category/post_tag и ингредиентных архивов принять отдельное решение по качеству. ## Оптимизация для AI-поиска и ответов нейросетей

Здесь **GEO** означает оптимизацию видимости в генеративных ответах, **AEO** — в системах, отвечающих на вопросы. Практическая цель Cooklook: чтобы поисковая система могла найти нужный рецепт, правильно извлечь условия приготовления и сослаться на исходную страницу. Попадание текста в обучающую выборку и его использование в актуальном поисковом ответе — разные процессы.

### AI-1. P1 — доступ к публичным страницам и настройки участия

Сначала выполнить пункты 1–6 основного аудита: пригодный к индексации HTML, корректные Recipe-данные, устойчивые URL, очищенная sitemap. Для Google требуется индексируемая страница, допускающая показ сниппета; отдельная «AI-schema» не нужна. Серверный вывод рецептов в Cooklook уже полезен: содержание не зависит от нажатия кнопок и AJAX. [Google: AI features and your website](https://developers.google.com/search/docs/appearance/ai-features).

На рабочем сайте проверить `robots.txt`, robots meta и `X-Robots-Tag`, а также CAPTCHA, CDN/WAF, HTTP 403/429/5xx и редиректы. Пустой локальный robots.txt не подтверждает доступность production. Основной рецепт должен возвращаться гостю в HTML без входа и персональных cookie. Для выбранных поисковых агентов обеспечивать доступ только к публичному содержимому; кабинет, редактор и личное избранное не открывать.

**Актуальная отдельная проверка Google:** в Search Console проверить **Search generative AI control**, включая наследование от родительского ресурса. Этот переключатель управляет участием в генеративных функциях Search отдельно от обычной поисковой выдачи. Для продвижения Cooklook в таких ответах участие должно быть разрешено; состояние текущего аккаунта неизвестно. Не следует считать разрешённый Googlebot достаточным подтверждением этой настройки. [Google: Search generative AI control](https://support.google.com/webmasters/answer/16908024).

`nosnippet`, `max-snippet` и `data-nosnippet` также влияют на использование текста в AI-функциях Google Search. Проверить, не закрывают ли они весь полезный текст рецепта. Не удалять существующие ограничения автоматически: они могут отражать намерение владельца; поддержка конкретных директив у других платформ проверяется отдельно.

### AI-2. P1 — разделить поисковых агентов, запросы пользователей и обучение

| Платформа / агент | Назначение и решение для Cooklook |
| --- | --- |

| Claude-SearchBot / Claude-User | Соответственно поиск и получение страницы по запросу пользователя. Anthropic описывает управление обоими через robots.txt |

| PerplexityBot / Perplexity-User | Соответственно поиск и пользовательское получение страницы; не предназначены для обучения базовых моделей. Для Perplexity-User документация отмечает, что robots.txt обычно игнорируется |

Назначения и различия приведены по официальным описаниям: [Google crawlers](https://developers.google.com/crawling/docs/crawlers-fetchers/google-common-crawlers#google-extended), [OpenAI Crawlers](https://developers.openai.com/api/docs/bots), [Anthropic crawlers](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler), [Perplexity Crawlers](https://docs.perplexity.ai/docs/resources/perplexity-crawlers).

**Рекомендуемая политика:** разрешать необходимый поисковый доступ к публичным рецептам; решение об обучении принимать отдельно по каждому провайдеру. Для Google-Extended учитывать, что он охватывает и grounding вне Google Search, поэтому его нельзя описывать только как «бот обучения». Никакие правила в рамках аудита не включены и не отключены.

При настройке отдельных групп robots.txt проверить применяемые к ним ограничения: специфическая группа может изменить действие общей группы `User-agent: *`. Не копировать безусловный `Allow: /` поверх существующей политики. Robots.txt не является механизмом авторизации. Исключения CDN/WAF проверять по официальным способам идентификации/IP, где они опубликованы; один подставленный User-Agent не доказывает происхождение запроса. Не отключать защиту всего сайта ради доступа робота.

### AI-4. P2 — подтвердить происхождение, опыт и актуальность

Предлагается добавить видимые сведения об авторе рецепта, авторе адаптации и проверяющем, если такие роли действительно были. Для адаптированного материала указать проверенный источник и характер изменений; для собственного — собственные фотографии и полезные наблюдения приготовления. Отдельная страница редакции может описывать, как проверяются время, пропорции и исправления. Не приписывать техническому аккаунту кулинарную экспертизу и не ставить отметку «проверено» автоматически.

Обновлять даты при содержательных изменениях и кратко пояснять значимые исправления, например пропорций или времени. Дополнять уже полезные рецепты собственным опытом вместо массовых страниц под каждую формулировку вопроса. Такой подход соответствует [рекомендациям Google по оптимизации для генеративного поиска](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide); он не является гарантированным фактором цитирования.

### AI-5. P3 — дополнительные форматы оценивать как эксперимент

- **`llms.txt`, `llms-full.txt` и Markdown-копии:** не обязательная доработка Cooklook. Google прямо сообщает, что специальные AI-файлы не улучшают видимость в его поиске. Для других систем эксперимент имеет смысл лишь при подтверждённом сценарии использования, синхронизации с HTML и измеримом результате. Отсутствие такого файла не является выявленной ошибкой. [Google: что не требуется для AI-поиска](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide).
- **Разметка:** сначала исправить существующую Recipe и связанный граф; не добавлять вымышленную «GEO-schema», ложные оценки или невидимые ответы. FAQ может быть полезен читателям без обещания специального результата в поиске.
- **Формат текста:** не дробить рецепт искусственно на страницы или отрывки заданной длины. Организовать материал по реальным действиям и вопросам; специальной универсальной длины «AI-абзаца» нет.
- **Актуальность:** после реального изменения рецепта обновлять sitemap/lastmod. При необходимости рассмотреть IndexNow для участвующих поисковиков, например Bing; это уведомление об изменении, не гарантия индексации или упоминания. [Bing об IndexNow и AI Search](https://blogs.bing.com/webmaster/2026/2/Introducing-AI-Performance-in-Bing-Webmaster-Tools-Public-Preview/).

Не отдавать ботам отдельный приукрашенный рецепт, скрытый от посетителей, не вставлять инструкции «нейросетям обязательно цитировать Cooklook» и не создавать массовые дубли по всем комбинациям ингредиентов. Это не устраняет проблемы доступности и качества, найденные в основном аудите.

Такая проверка даст наблюдения, но без контроля прочих факторов не докажет причинность изменений.

**Техническая приёмка:** публичные выбранные URL доступны нужным агентам; настройки участия проверены; название, факты, ингредиенты и шаги присутствуют в исходном HTML; якоря работают; JSON-LD согласован с текстом; служебные страницы сохраняют ограничения.

**Оценка результата:** раздельно отслеживать показы, ссылки/цитирования, переходы и целевые действия, например сохранение рецепта. Указать исходные значения и период наблюдения, затем назначать реалистичные цели. Не обещать фиксированное число упоминаний за срок и не выдавать единичный удачный ответ за устойчивую видимость. - `http://www.cook-look.ru/` → 301 → `https://www.cook-look.ru:443/` → 301 → `https://cook-look.ru/` → 200. HTTPS-вариант с `www` имеет один редирект. Упрощение цепочки и удаление явного `:443` относятся к конфигурации сервера при выпуске, а не к PHP-шаблону.
- `/sitemap.xml` и `/wp-sitemap.xml` возвращают 301 на `/sitemap_index.xml`, конечный ответ — 200. В robots.txt сейчас указан старый вход `https://cook-look.ru/sitemap.xml`; при настройке robots указать конечный адрес карты.

- `/page-sitemap.xml` содержит только `/` и `/account/`. В первых картах рецептов, категорий и ингредиентов — соответственно 1001, 643 и 1000 URL; все `<loc>` в этих трёх файлах используют основной HTTPS-хост. Остальные части карт не обходились; это не полный подсчёт контента или проиндексированных страниц.

**Пункт 14: перенос счётчика просмотров — выполнено 16.10.2026.** [recipe-views.php](../inc/recipe-views.php) и [recipe-views.js](../static/js/recipe-views.js) сохраняют поле `_recipe_views` и его использование для сортировки популярных рецептов. Запись выполняется отдельным AJAX-запросом после загрузки страницы, с прежней блокировкой параллельных обновлений. До выдачи HTML счётчик больше не читает/пишет метаданные и не сбрасывает их кеш. Это перенос работы: фоновый запрос по-прежнему загружает WordPress и обновляет БД; снижение общей серверной нагрузки на каждый просмотр не заявляется.

Правила подсчёта и кеша:

- Один запрос на загрузку видимой страницы рецепта; скрытая вкладка и prerender ждут активации. Повторные события видимости и восстановление того же документа из bfcache не создают второй запрос. Обычная перезагрузка считается новым просмотром.
- Скрипт подключается только к опубликованному рецепту без пароля, вне preview/feed/embed. Сервер также проверяет доступность рецепта, метод POST, точное совпадение Origin с сайтом и nonce конкретного рецепта; ответ запрещено кешировать. Гости и вошедшие читатели поддерживаются.
- Истёкший либо относящийся к другой сессии nonce из кешированного HTML заменяется свежим в ответе 403 **без записи**; клиент повторяет запрос с ним не более одного раза. Сетевые ошибки, занятая блокировка и ошибки записи не повторяются автоматически, чтобы не удваивать уже принятый просмотр. HTML-кеш сайта этим изменением не включается; правила изоляции персональных страниц остаются отдельной задачей.
- Пустой User-Agent и известные маркеры поисковых/AI-роботов, предпросмотра и headless-клиентов пропускаются до обращения к БД. Это эвристика, а не проверка настоящих IP роботов и не защита от намеренной накрутки. Модуль не сохраняет IP, не добавляет cookies или идентификаторы посетителя.
- Показатель теперь отражает приблизительное число загрузок видимых страниц с работающим JavaScript, а не все HTTP-хиты или уникальных людей. Без JS, при блокировке запроса или уходе до загрузки просмотр может не попасть в счётчик. Исторические значения не пересчитываются; сравнение периодов должно учитывать смену методики.

## Проверки после исправлений

| Проверка | Критерий приёмки |
| --- | --- |
| Главная, рецепт, категория, ингредиент, архив и page/2 | Ожидаемый статус, осмысленный title, видимый главный заголовок, согласованные robots и один canonical |
| Невалидные фасеты и page за пределами выдачи | 404; нет редиректа всех ошибок на главную/каталог |
| Фильтры | AJAX = полная загрузка = Back/Forward; сброс полностью удаляет старые индексированные ключи |
| Пагинация | Работает без JS; ссылки не проходят через 301; page/2 не канонизируется на page/1 |
| Служебные URL | Noindex независимо от общей настройки сайта; отсутствие в sitemap; персональные страницы защищены авторизацией и кеш-политикой |
| JSON-LD | Валидный JSON и отсутствие критических ошибок Recipe/Breadcrumb; реальные фото, питание, автор, времена, оценки |
| Sitemap и robots | 200 на конечном URL; карта содержит выбранные канонические публичные страницы; правила не блокируют нужные изображения/CSS/JS |
| Картинки | Правильные размеры, srcset/sizes, alt и приоритет загрузки; нет подмены фото заглушкой в Recipe |
| Реклама | Sponsored на платных ссылках, зарезервированное место под согласованные форматы |
| Мобильность и скорость | Нет горизонтального переполнения и перекрытия контента; измерены LCP/INP/CLS и TTFB на типичных страницах |
| Production | Проверены HTTP→HTTPS, выбранный хост, отсутствие цепочек редиректов и URL локального домена в HTML/XML |
| AI-поиск | Проверены правила поисковых агентов, CDN/WAF и участие в генеративном поиске; источник, факты и инструкции видны в HTML; есть исходные показатели по AI-6 |

Для разметки использовать [Rich Results Test](https://search.google.com/test/rich-results) и [Schema Markup Validator](https://validator.schema.org/); локальный домен недоступен внешним валидаторам, поэтому нужен ввод кода или доступное согласованное окружение. Schema.org проверен на этапе 5 по публичному URL и локальному коду; Google Rich Results Test не вернул результат. URL Inspection в Search Console и диагностика ресурса в Яндекс Вебмастере остаются открытыми.

Ориентиры хороших Core Web Vitals на 75-м перцентиле: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. Отдельный быстрый локальный запрос не подтверждает выполнение этих показателей; нужны полевые данные, а при их отсутствии — явно обозначенные лабораторные измерения. [Web Vitals](https://web.dev/articles/vitals).

Дополнительно на рабочем домене проверить архивы авторов/дат, attachment-страницы, варианты URL с параметрами, страницы комментариев, актуальность lastmod, доступность изображений и отсутствие ошибок/отладочного вывода PHP. Это список незавершённых внешних проверок, а не установленные неисправности темы.
