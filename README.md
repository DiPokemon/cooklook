# Cooklook

Классическая тема WordPress для сайта рецептов. Основной код находится в PHP-шаблонах, `functions-parts/`, `inc/` и `static/js/`. Рабочие стили — `static/css/style.min.css`; исходники — `static/css/*.scss`.

## Документация

- [Технический SEO-аудит и оптимизация для AI-поиска](docs/technical-seo-audit.md) — план от 16 октября и повторная проверка реализации 17 октября 2026 года: метаданные Yoast, пагинация, восстановление фильтров, изображения и остающиеся редакционные задачи.
- [Сводка повторной проверки SEO](docs/seo-recheck-summary.json) — результаты тестов, HTTP-обхода и путь актуального проверенного выпуска; публикация на рабочий сайт не выполнялась.

## Модель данных и совместимость

Рефакторинг сохраняет существующие имена полей, публичные URL и способы хранения.

| Данные | Хранение |
| --- | --- |
| Рецепты | Тип записи `recipe`, архив `/recipes/` |
| Блог | Тип записи `blog_post` |
| Категории / ингредиенты для фильтра | `recipe_category` / `recipe_tags` |
| Порции, время, питание, регион, внешний ID | Поля Carbon Fields `recipe_*`; простые значения находятся в `_recipe_*` в postmeta |
| Состав рецепта | Complex-поле `ingridients`: `ingridient_name`, `ingridient_value` |
| Шаги | `recipe_step`: `recipe_step_text`, `recipe_step_image` |
| Исходные шаги | `original_recipe_step`: `original_recipe_step_text` |
| Голос пользователя | usermeta `user_votes`, карта ID рецепта → `like` / `dislike` / `none` |
| Избранное | Таблица `{prefix}favorite_recipes` |
| Поисковые запросы | `{prefix}pending_searches`, `{prefix}popular_searches`, `{prefix}rejected_searches` |

Опечатки в именах ингредиентов сохранены намеренно. Complex-поля читаются и сохраняются через Carbon Fields. Простой текст и числа читаются из штатного кеша метаданных WordPress с теми же ключами. Существующие голоса, счётчики, идентификаторы, термины и связи не пересчитываются и не мигрируют.

При активации темы или первом входе администратора создаются только отсутствующие служебные таблицы. Существующие таблицы не перестраиваются; добавляется служебная опция `cooklook_tables_checked`. Все записи в базе во время автоматических тестов заменены данными в памяти.

## Устройство

- `inc/recipe-helpers.php`: чтение данных, нормализация входных значений, проверка AJAX nonce, блокировки конкурентных изменений, общий цикл карточек.
- `inc/recipe-query.php`: единые фильтры, сортировка, публичная видимость рецептов и пагинация. Пустые метаданные не исключают рецепты из сортировки.
- `filters-handler.php`: каталог и загрузка подкатегорий. `sort_posts` сохранён как совместимое имя действия и возвращает тот же JSON-конверт, что `filter_recipes`.
- `functions-parts/recipe_rating.php`: повторяемые без изменения результата запросы голосования; переключение голоса корректирует оба счётчика.
- `functions-parts/favorite_recipes.php`: избранное только текущего авторизованного пользователя; список ID читается один раз за запрос.
- `recipe_manager.php`, `recipe_importer.php`: административные действия с проверкой nonce, роли и права редактирования конкретной записи.
- `static/css/admin-styles.scss` и CSS-варианты: только стили менеджера рецептов и модерации поиска, без общих сбросов и шрифтов сайта. Подключаются исключительно на этих двух экранах. Таблица шагов менеджера имеет фиксированную раскладку 50/50, поля растут по высоте, превью ограничено 100 px с сохранением пропорций. Изображения остальных экранов оформляются штатными стилями WordPress.
- `template-parts/schema.php`: JSON-LD через `wp_json_encode`, без ручной конкатенации JSON.
- `static/js/filters.js`: единое состояние сортировки, фильтров, страниц и URL; отмена старых запросов.
- `static/css/catalog.css`: отображение фильтров, мобильной панели и выбора ингредиентов; подключается только в каталоге после общих стилей и не требует Sass.
- `page-account.php`, `template-parts/account-profile.php`, `inc/account.php`: личный кабинет на существующей странице `/account/`, избранное, редактирование профиля и выход. Имя, фамилия, отображаемое имя, описание, почта и пароль используют штатные поля WordPress. Если шорткод WP-Recall зарегистрирован и присутствует в содержимом страницы, сохраняется кабинет плагина. Содержимое страницы в базе не переписывается.
- Доступ к экранам `/wp-admin/` и панели WordPress разрешён только с правом `manage_options`. Проверка выполняется на `init`, до построения административного меню. Обычный пользователь перенаправляется в `/account/`; административные возможности существующих ролей в базе не меняются. `admin-ajax.php` и `admin-post.php` остаются доступны как служебные обработчики: каждый обработчик обязан самостоятельно проверять nonce и права. Это ограничение интерфейса не заменяет настройку ролей и прав REST API сторонних плагинов.
- Формы кабинета проверяют nonce и берут ID исключительно из текущей сессии. Сохранение разрешает только перечисленные поля; переданный ID, роль и произвольные метаданные игнорируются. Почта и пароль требуют текущего пароля; новый адрес применяется только после подтверждения в той же учётной записи. Запрос хранится в стандартном `_new_email`, действует 24 часа, отменяется в кабинете. Ошибка отправки письма не меняет почту и восстанавливает предыдущий запрос. Пароли хешируются и сессия обновляется средствами WordPress; сами пароли не возвращаются в HTML.
- `static/css/account.css` и `static/css/layout.css`: оформление кабинета и общие исправления, включая пропорции логотипа в футере; подключаются после скомпилированных стилей без сборки Sass.
- `tests/`: проверки без подключения к рабочей базе.

Публичный поиск использует Relevanssi, если он активен, и стандартный WordPress в остальных случаях. В обоих случаях выдаются опубликованные рецепты без пароля. Статистика учитывает отправленные поисковые запросы; ввод каждой буквы больше не создаёт записи модерации. Повторения и число записей ограничиваются; исходный IP в этой статистике не сохраняется.

В каталоге включаемые ингредиенты объединяются условием AND: рецепт должен содержать все выбранные ингредиенты. Исключаемые ингредиенты используют NOT IN. Фильтры остаются в границах открытой категории или тега. Сортировка по времени идёт по возрастанию, по просмотрам — по убыванию.

Кириллические slug и URL обрабатываются отдельно от обычного текста: `sanitize_text_field` удаляет из них процентную кодировку. На главной проверяется существование выбранных категорий; если все сохранённые ссылки устарели, показываются существующие корневые категории по числу рецептов. Настройки в базе при этом не переписываются.

## Административные сценарии

Обновление существующих рецептов открывается в меню «Обновление рецептов» (`admin.php?page=cooklook-recipe-importer`). Его функции и инициализация Carbon Fields имеют префикс темы, чтобы не конфликтовать с установленным отдельно плагином Recipe Importer.

Менеджер публикует только черновики. Он сохраняет изображения и служебные данные шагов, проверяет непустой текст и не меняет время, если поле не передано. Ошибка публикации отдельно сообщает, что шаги уже сохранены.

CSV обновляет только существующие рецепты по `recipe_id`. Неизвестный или неоднозначный ID пропускается. Формат: UTF-8, разделитель запятая, стандартные CSV-кавычки; BOM допустим. Ограничения: 2 МБ, 500 строк; клиент обрабатывает по 5 строк за запрос.

Поддерживаемые колонки:

- `recipe_id` — обязательная;
- `image` — URL изображения;
- `ingredients_names`, `ingredients_quantities` — парные списки одинаковой длины;
- `steps_texts`, `original_steps_texts` — списки шагов.

Разделитель списков — ` | `. Отсутствующие или пустые необязательные колонки не очищают данные. Тексты шагов обновляются с сохранением изображений по индексу; при изменении порядка шагов нужно проверить соответствие изображений. Время, счётчики, заголовки, статусы и таксономии импортёр автоматически не перезаписывает. Одна строка проверяется до записи; при прерывании партии ранее обработанные строки могут быть сохранены. Повторная загрузка обновляет записи по тому же ID; уже установленное изображение с тем же `_source_url` повторно не скачивается.

Блокировки MySQL/MariaDB `GET_LOCK` защищают голоса, избранное, импорт и менеджер от параллельных изменений через эти обработчики. При занятой или недоступной блокировке операция отклоняется и предлагает повторить попытку. Это не транзакционная миграция и не защита от параллельных правок сторонними плагинами.

Обработка изображений применяется только к изображениям, прикреплённым к рецепту, и только при наличии Imagick и файлов водяных знаков. Неудачная обработка не заменяет исходный файл. Существующая логика преобразования успешной загрузки сохранена.

## Проверка

Не требуется устанавливать JavaScript-зависимости для следующих команд:

```sh
php tests/run.php
php tests/account.php
php tests/seo.php
php tests/recipe-views.php
php tests/recipe-regions.php
node tests/filters.test.cjs
node tests/comments.test.cjs
node tests/recipe-views.test.cjs
node tests/run-js.cjs
php vendor/bin/parallel-lint --exclude .git --exclude vendor .
php vendor/bin/phpcs --standard=phpcs-security.xml.dist
```

Проверка настоящего генератора пагинации WordPress:

```sh
php tests/wordpress-core.php
```

Она ищет WordPress над каталогом темы. Для другого расположения задайте `COOKLOOK_WP_ROOT`. Скрипт читает только файлы ядра, не загружает `wp-config.php` и не обращается к базе.

Набор регрессий проверяет в том числе повторные голоса, смену голоса и откат при ошибке записи; изоляцию избранного; сохранение изображений и времени; ошибки и длинные строки CSV; права доступа; модерацию комментариев; безопасный JSON-LD; мобильную сортировку; сброс фильтров и запоздавшие AJAX-ответы.

Проверки SEO дополнительно покрывают промежуточные ссылки хлебных крошек, фотографии Recipe и шагов, исключение непроверенного питания, robots/sitemap при разрешённой индексации, неверные фасеты и параметры ингредиентов с индексами. `inc/seo.php` задаёт правила через Yoast и штатные фильтры WordPress; отдельные meta-теги или карты тема не печатает. На служебных страницах сохраняется запрет кеширования, локальный общий `noindex` не снимается.

Для списка редакционных доработок выполните `php tools/recipe-seo-report.php > recipe-review.json` с PHP, настроенным для базы этой копии WordPress. Можно задать `COOKLOOK_WP_ROOT`; скрипт загружает WordPress и читает опубликованные рецепты без пароля, не меняя их поля или статусы. Снимок локальной копии: [seo-recipe-review.json](docs/seo-recipe-review.json). Правила исправления данных и результаты второго этапа приведены в [SEO-плане](docs/technical-seo-audit.md).

Локальная редактура описаний от 17.10.2026: [пакет десяти рецептов](docs/seo-editorial-batch.json) содержит согласованные с исходным текстом excerpt, снимки ингредиентов/шагов и отдельные замечания по времени; [отчёт](docs/seo-editorial-check.json) подтверждает применение и отображение. `php tools/apply-recipe-summaries.php` выполняет только предварительную сверку; `--apply` сохраняет описания через WordPress с резервной копией в `build/` и транзакцией. Инструмент ограничен локальным `http://cooklook/`, запрещает подмену изменившихся фактов или заполненного другим текстом excerpt и безопасен при повторном запуске. Для работы нужны PHP с mysqli, локальная БД и обычный непостоянный объектный кеш; при другом расположении WordPress задайте `COOKLOOK_WP_ROOT`. Служебная работа WP-Import-Export-Lite, почта и внешние HTTP-запросы исключены только в CLI-процессе. Резервная копия содержит прежние excerpt и даты; для отката возвращайте только excerpt через WordPress, сохраняя более поздние независимые правки. Новые описания находятся в БД, поэтому ZIP темы их не переносит. Фактическое время ещё требует редакционного подтверждения; автоматического заполнения минут нет.

Изображение записи должно показывать готовое блюдо. Без него Recipe не выводится; фотографии процесса используются только в видимых шагах. Для новых загрузок зарегистрированы кадры 1:1, 4:3, 16:9; старые изображения автоматически не пересоздаются. Историческое питание на 100 г остаётся в данных и интерфейсе, но не передаётся в Recipe до проверки единиц и массы порции. Редактор показывает предупреждения, не блокируя сохранение и не меняя статус рецепта.

P2: `inc/seo-metadata.php` задаёт стандартные title/description через Yoast, сохраняя индивидуальные значения редактора. Полный текст рецепта выводится через `the_content()`. Для изображений категорий предпочтительно новое поле `category_image_id`; старое URL-поле поддерживается без миграции. `inc/media.php` формирует адаптивные изображения и баннеры. Подробности и результаты проверок — в [SEO-плане](docs/technical-seo-audit.md).

Дополнительная проверка на локальном WordPress: `php tests/seo-wordpress.php` (PHP с доступом к базе, активная тема Cooklook; при необходимости `COOKLOOK_WP_ROOT`). Она не сохраняет тестовый контент или настройки: полный текст и обычные permalink settings подставляются только в память текущего процесса. Основные регрессионные тесты по-прежнему не подключаются к базе. WebP-варианты баннеров пересоздаются командой `php tools/build-banner-images.php` с Imagick/WebP; JPEG-оригиналы остаются fallback.

Для AI-поиска HTML и Recipe используют `cooklook_recipe_facts()`; ингредиенты независимы от шагов, прежние `#step_N` сохранены. Yoast владеет общим графом, тема добавляет только Recipe через его фильтр; без Yoast работает самостоятельный fallback. Историческое питание не публикуется как проверенное, наличие массы порции не включает его автоматически.

По решению владельца автор всех рецептов — CookLook: единый `cooklook_recipe_author()` используется в HTML и Recipe (`Organization`). Первоисточник не публикуется, включая `isBasedOn`; сохранённые `recipe_url` и прежние `recipe_public_source_*` не выводятся и не изменяются. Во вкладке «Авторство и пояснения» остаются необязательные сведения о проверяющем, адаптации, советах, изменениях и массе порции (`recipe_public_*`, `recipe_serving_mass`); заполняйте их подтверждёнными данными. Для краткого редакционного описания используется стандартный отрывок (excerpt). `tools/recipe-seo-report.php` показывает недостающие сведения и некорректные факты без требования заполнить индивидуального автора.

`php tests/seo-ai-wordpress.php` проверяет HTML/JSON-LD десяти существующих рецептов и безопасность новых полей без изменения БД (нужны локальный WordPress, Yoast и PHP с mysqli). `node tools/seo-ai-access.cjs https://cook-look.ru/` читает robots.txt, десять рецептов из sitemap и выполняет ограниченные User-Agent-пробы без авторизации; это не проверка реальных IP роботов и не настройка Search Console. Снимки: [локальная проверка](docs/seo-ai-local-check.json), [публичный HTTP-доступ](docs/seo-ai-access.json). Политика обучения в теме не изменяется; открытые условия завершения этапа 4 приведены в [плане](docs/technical-seo-audit.md).

`php tests/recipe-cards-wordpress.php` сравнивает шаги, изображения, описания и карточки всех опубликованных рецептов с исходным хранилищем Carbon Fields и проверяет отсутствие SQL при чтении уже загруженных метаданных. Нужен локальный WordPress с активной темой и PHP с mysqli; тест не записывает данные. Поле `recipe_step` использует `Cooklook_Cached_Post_Meta_Datastore`: формат Carbon Fields и штатная инвалидация кеша WordPress сохраняются. `php tools/seo-query-profile.php` повторяет восемь сценариев выдачи по три раза; сопоставимые результаты до/после сохранены в [SEO-плане](docs/technical-seo-audit.md).

Справочник регионов (`inc/recipe-regions.php`) хранится в отдельном для сайта transient на час. Изменение `_recipe_region` (включая массовое удаление), публикация/скрытие, смена типа или пароля через WordPress, удаление публичного рецепта и повторная активация темы сбрасывают кеш. Версия в неавтозагружаемой опции защищает от сохранения старой сборки после сброса; старые поколения истекают через час. Просмотры и оценки кеш не сбрасывают. Проверка выбранного региона остаётся запросом к актуальным данным с прежними правилами сравнения БД. Импорт напрямую через SQL должен вызывать `cooklook_invalidate_recipe_regions()` после завершения; штатный импорт темы использует WordPress/Carbon Fields. HTML-кеш страницы на сервере обслуживается отдельно.

`php tests/recipe-regions.php` проверяет инвалидацию, пустые данные, истечение срока, сбои и одновременную сборку/сброс в памяти. `php tests/recipe-regions-wordpress.php` сравнивает справочник и фильтрацию с настоящей БД; разрешены только записи кеша справочника, рецепты не изменяются. Для повторных замеров: `php tools/seo-region-profile.php legacy`, затем `php tools/seo-region-profile.php cold` и отдельным процессом `php tools/seo-region-profile.php warm`. Холодный замер сбрасывает только этот справочник. `node tools/seo-region-http-check.cjs` сверяет локальные HTTP/AJAX-ответы с сохранёнными исходным списком и интеграционным отчётом; после изменения набора рецептов эти два отчёта нужно обновить. Результаты — в [SEO-плане](docs/technical-seo-audit.md).

Ингредиенты (`inc/recipe-ingredients.php`) загружаются поиском: 2–100 символов, задержка ввода 300 мс, 20 результатов за запрос, максимум 100 страниц на один поисковый текст. Для более широких совпадений нужно уточнить название. GET `cooklook_search_ingredients` использует nonce `cooklook_catalog` и отдельный параметр `ingredient_page`, чтобы не пересекаться со служебным `page` плагинов админки. Поиск показывает непустые `recipe_tags`, использует штатное экранирование/кеш термов WordPress и одну дополнительную строку для признака следующей страницы без COUNT. Метаданные термов не загружаются. Отложенные запросы и ответы с устаревшим текстом игнорируются; ошибки загрузки/истёкший nonce сопровождаются подсказкой повторить поиск или обновить страницу.

В исходный HTML входят только выбранные значения: не более 20 включённых и 20 исключённых ингредиентов. Существующие пустые термы в сохранённых ссылках восстанавливаются; правила AND/NOT IN, фильтрация рецептов и пагинация сохранены. Шесть популярных вариантов остаются отдельными кнопками выбора. Новые ингредиенты ищутся через JavaScript, а выбранные значения и сами рецепты доступны в серверном HTML.

`php tests/recipe-ingredients.php` и `node tests/recipe-ingredients.test.cjs` проверяют границы входных данных, вывод, популярные варианты и устаревшие ответы. `php tests/recipe-ingredients-wordpress.php` сравнивает страницы поиска с полной выборкой на настоящей БД без записи данных. `php tools/seo-ingredient-profile.php` измеряет только рендер окна после загрузки WordPress, включая размер HTML и SQL; это не TTFB страницы. `node tools/seo-ingredient-http-check.cjs` проверяет локальные гостевые ответы, сохранение выбранного, архивы и пагинацию; сначала обновить интеграционный отчёт, а при смене тестовой БД — также набор выбранных значений в исходном профиле. Результаты и ограничения — в [SEO-плане](docs/technical-seo-audit.md).

Сортировки используют одно агрегирование по точному `meta_key`: время по возрастанию, просмотры по убыванию, затем дата и ID по убыванию. Отсутствующее значение считается нулём, дубли сводятся через `MAX(CAST(... AS DECIMAL(20,4)))`. Фильтр кухни передаётся отдельным аргументом `cooklook_recipe_region` и проверяет принадлежность ID подзапросом с точным `_recipe_region`. Это сохраняет сравнение значений по collation БД и избегает преобразования ключа в `LIKE` сервисом Carbon Fields. Остальные запросы Carbon Fields не меняются.

`php tools/seo-sort-profile.php` сохраняет SQL, EXPLAIN, EXPLAIN ANALYZE (MySQL 8.0.18+), девять прямых замеров и проверку кеша WP_Query для 24 сочетаний сортировок/фильтров. Команда не изменяет БД и не очищает кеши. `php tests/recipe-sorting-wordpress.php` сравнивает все страницы выдачи с исходными SQL из `docs/seo-sort-profile-before.json` и проверяет числовые значения, дубли, доступность, экранирование и пагинацию на SELECT/UNION-примерах без записи тестовых рецептов. Нужны локальные WordPress/Carbon Fields и PHP с mysqli. `node tools/seo-sort-http-check.cjs` сравнивает SSR/AJAX и выбранную сортировку на основе актуального `docs/seo-sort-profile-after.json`. Методика, результаты и открытый повтор на рабочей БД — в [SEO-плане](docs/technical-seo-audit.md).

Просмотры `_recipe_views` записываются отдельным POST после загрузки видимой страницы (`inc/recipe-views.php`, `static/js/recipe-views.js`). GET/HEAD не изменяют счётчик. Проверяются Origin, nonce рецепта и публичность записи; известные User-Agent роботов исключаются эвристически. Истёкший nonce из HTML-кеша обновляется без записи с одним повтором; после сетевой ошибки или ошибки записи повторов нет. Это приблизительные просмотры с JavaScript, а не уникальные посетители или прежние HTTP-хиты. Дополнительные cookies/IP-идентификаторы не сохраняются. Методика и ограничения — в [плане](docs/technical-seo-audit.md).

`php tests/recipe-views-wordpress.php` проверяет настоящий WordPress/AJAX с перехватом записи счётчика в памяти. `php tools/seo-view-profile.php` проверяет отсутствие старого обработчика до HTML и показывает его изолированную стоимость при наличии. Оба инструмента используют существующий локальный рецепт 9885, требуют PHP с mysqli и не увеличивают реальные просмотры; `COOKLOOK_WP_ROOT` поддерживается.

`phpcs.xml.dist` остаётся полным историческим набором WordPress/WPThemeReview: весь старый код ещё не приведён к каждому его требованию. Отдельный `phpcs-security.xml.dist` проверяет исправленные границы запросов и новые фрагменты шаблона рецепта.

Мобильный поиск ингредиентов дополнительно проверен 17.10.2026 на пяти размерах окна, включая ширину 320 px и высоту 320 px: [сценарии и результаты](docs/seo-ingredient-mobile-check.json), [снимок](docs/seo-ingredient-mobile.jpg). Проверены прокрутка и подгрузка поиска, включение/исключение, сброс, сортировка, перезагрузка и история браузера. Исправления кода не потребовались. Это локальная проверка Chromium; настоящие мобильные устройства, рабочая версия и полевые показатели остаются отдельной проверкой.

Локальная группа сравнения редакционных описаний: [семь пар и три исключения](docs/seo-editorial-cohort.json), [снимок 80 рецептов](docs/seo-cohort-inventory.json), [отчёт проверки](docs/seo-editorial-cohort-check.json). Контрольные рецепты 9891, 9887, 9901, 9899, 9890, 9892 и 9896 зарезервированы от дальнейшей редактуры на период сравнения; это правило работы, а не блокировка в редакторе. Повторная проверка:

```sh
php tools/seo-cohort-snapshot.php > build/seo-cohort-inventory.json
node tools/seo-cohort-check.cjs build/seo-cohort-inventory.json
php tools/seo-cohort-http-check.php
```

Для снимка нужны локальный WordPress, PHP с mysqli и обычный непостоянный объектный кеш; поддерживается `COOKLOOK_WP_ROOT`. SQL-запись, внешние запросы, почта и служебная работа WP-Import-Export-Lite отключаются только в CLI-процессе. Проверка на Node.js 18+ сверяет свежий снимок с сохранёнными фактами и критериями, а PHP с DOM проверяет HTML всех 14 локальных страниц гостевыми GET-запросами без JavaScript и редиректов. При изменении рецептов сначала разберите расхождение; не перезаписывайте исходную выборку автоматически. Это проверка локальной подготовки: рабочие URL, исходная поисковая статистика и реальные AI-ответы ещё не получены, вывод об эффекте изменений не сделан.

## Зависимости и выпуск

Для кабинета нужна опубликованная страница WordPress с ярлыком `account`, без родительской страницы, с шаблоном «Личный кабинет». Создайте её через «Страницы → Добавить страницу», если она отсутствует на целевом сайте. Перенос файлов темы не создаёт страницы в базе: наличие `page-account.php` само по себе не устраняет 404 по `/account/`. Существующую страницу кабинета и её содержимое сохраняйте.

PHP-зависимости зафиксированы в `composer.lock`, в том числе Carbon Fields 3.6.3. Каталог `vendor/` необходим на сервере; его нельзя исключать из архива темы. Для сборки нужны PHP 7.4+ с ZipArchive, Composer PHAR и уже установленные зависимости из lock-файла:

```sh
php tools/build-release.php --composer=/path/to/composer.phar
php tests/release-wordpress.php build/release-<id>/extracted/cooklook
```

Первая команда создаёт новый каталог `build/release-<id>/` с `cooklook.zip`, контрольными суммами в `manifest.json` и распакованной копией. Она копирует тему в отдельный каталог, там выполняет Composer `--no-dev --optimize-autoloader` без сети, плагинов и scripts, затем проверяет каждый файл архива. Рабочий `vendor/` сохраняется. В ZIP входят только перечисленные в сборщике файлы темы и рабочие зависимости; отчёты `docs/`, тесты и инструменты исключены. При добавлении корневого шаблона или нового каталога обновляйте список сборки. `npm run bundle` вызывает тот же сборщик; путь PHAR задаётся через `COOKLOOK_COMPOSER_PHAR` или аргумент `--composer` после `--`.

Вторая команда требует PHP с mysqli и установленный локальный WordPress без постоянного object-cache drop-in (`COOKLOOK_WP_ROOT`, если он расположен отдельно). Проверка загружает тему именно из распакованного архива через фильтры текущего процесса, запрещает SQL-запись и проверяет зависимости, карточки, три сортировки, поиск ингредиентов, десять рецептов и пути ресурсов. Transient-кеш остаётся в памяти процесса; WP-Import-Export-Lite исключается только в этом процессе из-за служебных записей при запуске. Настройки активной темы и плагинов не меняются. Это проверка комплектности на локальных данных; публикацию, совместимость со всеми плагинами и повторные замеры рабочей базы она не заменяет. [Результат подготовки выпуска](docs/seo-release-preflight.json). Перед публикацией сохраните текущую тему и базу для отката; после обновления согласованно очистите кеш страниц и проверьте опубликованные URL по SEO-плану.

JavaScript использует jQuery из WordPress в режиме noConflict. URL AJAX формируется через `admin_url`, поэтому установка WordPress в подкаталоге поддерживается. Версии файлов основаны на времени изменения. После обновления PHP и JavaScript очищайте кеш страниц вместе: AJAX-контракты теперь используют nonce и JSON с `success/data`.

Исходный npm-набор с `node-sass` не обновлялся в этом рефакторинге. Исправлены пути его команд; общие стили не пересобирались. Исправления отображения каталога находятся в отдельном `static/css/catalog.css`. Доступ к npm registry в текущей среде отсутствовал. Обновление Sass и остальных сборочных зависимостей требует отдельной проверки lock-файла и визуального сравнения CSS.

## Проверка на запущенной копии сайта

16 октября 2026 года выполнена браузерная проверка `http://cooklook/` после запуска OpenServer: WordPress 7.1.3, PHP 8.1.9. Проверены настольный экран 1440 × 1000 и мобильный 390 × 844.

- Главная, каталог, архив категории и кириллического тега, полный рецепт, JSON-LD, гостевое избранное.
- AJAX-загрузка подкатегорий, фильтр кухни и пустая выдача, два включённых ингредиента и один исключённый, обе сортировки, сброс и удаление отдельного ингредиента.
- Пагинация и возврат браузером. Для кириллического тега результаты второй страницы после AJAX совпали с результатами после полной перезагрузки.
- Автодополнение поиска с Relevanssi и отправка поисковой формы. Ошибок JavaScript в проверенных сценариях не обнаружено.
- Запросы без корректного nonce к каталогу, голосованию, избранному и комментариям получили HTTP 403. Административные AJAX-действия без входа получили HTTP 400 без выдачи данных.

После входа администратором дополнительно проверены:

- Кабинет и футер на узком экране: доступные действия, карточки профиля, пропорции логотипа. Гостевой запрос к кабинету показывает вход без административных ссылок; ответ запрещает кеширование персональной страницы.
- Добавление и удаление избранного с проверкой после перезагрузки; сохранение голоса, переключение и снятие оценки. Исходное избранное и оценка восстановлены.
- Публикация комментария и вложенного ответа. Исправлена навигация только к фрагменту URL: теперь новая запись загружается с сервера. Проверены снятие одобрения, скрытие от гостя и повторное одобрение.
- CSV-импорт ингредиентов и двух шагов в отдельный тестовый черновик: сохранились время и изображение первого шага. Публикация через менеджер сохранила данные и новое время; после публикации обновляются счётчики и остаётся сообщение об успехе.
- Загрузка PNG через WordPress: пиксели загруженного файла отличаются от оригинала и совпадают с результатом `process_image` под PHP 8.1 с Imagick.

Тестовые комментарии 19 и 20 и рецепт 10207 (`Cooklook QA — временный рецепт проверки 2026-10-16`, внешний `recipe_id=2026101601`) перемещены в корзину. Тестовое изображение 10209 (`cooklook-qa-image.png`) оставлено в медиатеке связанным с этим рецептом. Рабочие рецепты не импортировались и не публиковались. Миграции и правки настроек базы не выполнялись; обычные просмотры и поиск могут обновлять штатные счётчики.

В двух независимых сессиях (`admin` во встроенном браузере, `dimon` в Chrome) дополнительно проверены:

- Избранное: сохранение вторым пользователем не меняет список администратора; добавление и удаление того же рецепта администратором не удаляет сохранение второго пользователя.
- Голоса: у одного пользователя сохраняется лайк, у другого — дизлайк; снятие одного голоса не затрагивает другой. После теста рейтинг рецепта 9897 снова 3.8, у обоих нет голоса.
- Профиль: имя, отображаемое имя и описание второго пользователя сохраняются через форму; профиль администратора остаётся прежним. Исходные поля восстановлены. Итоговое избранное соответствует началу этого прогона: у администратора рецепт 9888, у второго пользователя пусто.
- Прямые ссылки на `/wp-admin/`, штатный профиль, список рецептов, менеджер, импорт и модерацию возвращают второго пользователя в кабинет. Панель WordPress скрыта. Администратор по-прежнему открывает менеджер; AJAX избранного и голосования работает после введения ограничения.
- Кабинет проверен на обычном настольном экране и при ширине 390 px: одна колонка полей, без горизонтального переполнения; логотип футера сохраняет размер 201.25 × 25 px.

`tests/account.php` отдельно проверяет подмену ID/роли, отсутствие входа, неверные nonce, некорректные поля, текущий пароль, точность обработки символов пароля, одноразовое подтверждение почты, срок действия ссылки, конфликт адресов и ошибку почтового транспорта. Тесты не отправляют писем и не подключаются к базе. Реальная доставка подтверждений и смена паролей существующих аккаунтов этим прогоном не выполнялись. Ветка кабинета с активным WP-Recall локально не проверена: шорткод здесь не зарегистрирован.

При диагностической загрузке WordPress обнаружены отдельные PHP notices о ранней загрузке переводов в установленных `wp-import-export-lite` и `wordpress-seo`. Они возникают в коде плагинов; их обновление и проверка совместимости требуют отдельной работы. Полная совместимость со сторонними плагинами и кешированием этим прогоном не подтверждается.

Исторически повреждённые счётчики и поля, записанные старым импортёром под ошибочными именами, автоматически не исправляются: для этого нужно отдельно обследовать копию базы.
